# Flux 1.8 — 2026-07-25

One change, but a structural one: an electricity plan is no longer three flat rates. It is a set of time bands, so a plan that charges different prices at different times of day can be described directly instead of approximated. The free window comes from the plan too, which means it moves on the day a plan switches rather than needing a server-side change timed to the minute.

## What's New

### Time-of-use pricing (T-1890, T-1891)

Until now a plan was a peak rate, a feed-in rate, and an off-peak savings rate, with the free window configured separately on the backend. That cannot express a plan like the one this was built for: free 10:00–15:00, a cheaper rate 01:00–06:00, and a standard rate the rest of the day.

A plan is now **a default rate plus the windows that deviate from it**. You enter the default, then add each exception — a start and end time, a Free toggle, and a rate when the window isn't free. Anything outside every window takes the default, which means a plan cannot accidentally be entered with a gap in it.

**Settings ▸ Pricing** shows each plan's date range and its bands, reading like `Free 10:00–15:00 · $0.2800 01:00–06:00 · $0.3500 default`, with feed-in on its own line. Validation in the app mirrors the backend's rules, so a plan the editor accepts is not then rejected by the server for something the editor could have caught.

### Plans hand over on a date

You can enter the next plan ahead of time and it takes over automatically on its start date. Ending the current plan on the date its successor starts gives that entire day to the successor — both plans carry the same date, and the editor's succession affordance now says exactly that, rather than the previous "the day before this start date" phrasing.

This is the part that makes a plan change a one-time data entry rather than something to be performed on the day.

### The free window follows the plan

The free (off-peak) window used to live in backend configuration, separate from the plan. It is now a property of the plan, so on a switch date the rates and the window change together, automatically.

Everything that depends on that window follows: the Day Detail chart shading, the off-peak card, the charge projection, and the cutoff suppression that stops the app predicting an empty battery when it will actually be charging. On the eve of a plan switch, the next-window predictions already use the incoming plan's window, because that is the window the battery will actually charge in.

A day whose plan has no free window now shows no window, rather than falling back to a default one that was never real.

### Costs come from the bands

A day's cost is the sum of each band's energy at that band's rate. Where the per-band measurement is available the cost is exact; where it isn't, the previous calculation is used instead, so nothing regresses.

**Every historical day's cost is unchanged.** The migration computed all 101 priced days under both the old and new formulas and would have refused to write anything if a single day differed. Day Detail and History agree with each other, and a day loaded from cache prices identically to one loaded online.

## Upgrade Notes

**This release requires a coordinated update.** The app and the backend must both be updated, and the pricing data must be migrated. That has already been done for the production system; the notes below matter only if you are deploying this from scratch.

The order is: deploy the backend, update the apps, run `cmd/migrate-pricing`, then enter any new plan.

- An app build older than this release cannot read migrated pricing data. It fails safely — no costs are shown, nothing crashes, nothing is written — but it will not display pricing until updated.
- `cmd/migrate-pricing` reports by default and writes only with `--apply`. It verifies every retained day's cost under both formulas and aborts before writing if any day differs, so a dry run that reports no mismatches is a genuine guarantee rather than a formality. It is idempotent, so re-running it is a no-op.
- `OFFPEAK_START` / `OFFPEAK_END` and the `OffPeakWindowStart` / `OffPeakWindowEnd` CloudFormation parameters are removed. Deploying leaves `/flux/offpeak-start` and `/flux/offpeak-end` behind as orphaned SSM parameters that nothing reads; they can be deleted at leisure.
- The poller container gains read-only access to the pricing table. The Lambda keeps sole write access.

Two deployment gotchas worth knowing, both hit during the production cutover and recorded in the spec's prerequisites:

- If `ContainerImageUri` is `:latest`, deploying the stack before the container image has finished building runs the new template against the old binary. Deploy the image first, or pin the image to its commit tag.
- Retagging `:latest` does not affect a running ECS deployment. ECS resolves a tag to a digest once when a deployment is created and pins it for that deployment's lifetime, so `aws ecs update-service --force-new-deployment` is required to make it re-resolve.
